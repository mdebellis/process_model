# Customer Portal execution snapshot

This is a fictional execution of the Customer Portal project plan, reported as
of **10 February 2027 at noon, UTC−08:00**. All people, artifacts, and timestamps
are illustrative. Open the combined
[process_model_with_examples.rdf](../ontologies/process_model_with_examples.rdf)
to inspect both the unchanged plan and this execution.

`pm:` denotes `https://in2use.com/process_model/`. The root
`pm:Customer_Portal_Execution` is a `prov:Activity`. Its eleven
`pm:Step_Execution` parts correspond to project-specific `Portal_…` Steps,
rather than directly to the reusable Method Omega definitions. The root's
qualified association identifies `pm:Customer_Portal_Plan` through
`prov:hadPlan`.

## What has happened

Six step executions have recorded ends: Kickoff Meeting, Create Project
Narrative, Create Wireframes, User Wireframe Interviews, Develop Wireframes,
and Use Case Interviews. Five remain in progress in this snapshot:
Requirements Acquisition, Create Detailed Requirements, Create Use Cases,
Write Use Cases, and Technical Design. The overall root Activity is also in
progress and is not included in those eleven step-execution counts.

Review Requirements, Requirements Acquisition Completed, Implementation,
Testing, and Rollout have no execution Activities in this example. Query
results call these **No execution recorded**: absence of an RDF assertion
does not generally prove that work has not started.

The execution tree uses actual `sulo:hasDirectPart` assertions. Its root has
Requirements Acquisition and Technical Design as direct parts. The requirements
branch contains the recorded composite and leaf performances. A property path
may select descendants for a query, but it does not add new hierarchy edges.
This is an Activity hierarchy in the same ontology, not a named graph,
`prov:Bundle`, or invented graph-membership relation.

Actual dates are recorded with `prov:startedAtTime` and, when present,
`prov:endedAtTime`. Linked `time:hasTime` intervals carry the same actual
endpoints. Ongoing Activities have no fabricated finish timestamp. Planned
dates remain on the separate `pm:has_scheduled_time` descriptions.

## Artifacts and participants

Six `pm:Document_Version` individuals record the available artifacts:
`Portal_Project_Brief_V1`, `Portal_Kickoff_Notes_V1`,
`Portal_Project_Narrative_V1`, `Portal_Wireframe_Interview_Notes_V1`,
`Portal_Wireframes_V1`, and `Portal_Use_Case_Interview_Notes_V1`.
They correspond to the project's planned Variables through
`pp:correspondsToVariable`. Activities use actual artifacts with `prov:used`;
produced artifacts identify their actual producer with `prov:wasGeneratedBy`.
The project brief is an available input, without an invented producer inside
this execution.

Actual people and roles are attached through `prov:qualifiedAssociation`,
`prov:agent`, `prov:hadRole`, and `prov:hadPlan`. These records describe
participation in the recorded execution and remain distinct from the plan's
intended assignments. Composite completion does not make a composite Activity
a second producer of an artifact generated by one of its children.

## Deliberate deviations

- Create Project Narrative ends at 18:00 on 2 February, one hour after its
  scheduled finish.
- The wireframe work ends at 16:00 on 5 February, one hour before its scheduled
  finish; both the leaf and its completed composite have actual ends.
- Technical Design starts at 10:00 on 10 February, before its scheduled
  15 February start and while Requirements Acquisition is still in progress.
  It uses the available wireframes and narrative. There is no recorded approved
  requirements decision or completed use-case artifact at this snapshot.

The plan and its finish-to-start transitions remain intact. Recording an early
start does not rewrite planned precedence or automatically create an OWL
inconsistency. Comparing the intended and observed timelines exposes the
deviation. Absence of required evidence is a reporting finding, not a fabricated
approval, rejection, or LLM evaluation.

The first four queries operate on asserted data. The graph queries return real
triples; they do not synthesize direct person links or ancestor/descendant edges.
The plan/actual table reports **Started; no end recorded** from the available
timestamps. The scenario documents the five ongoing performances; the query
label alone does not establish a universal completion rule. The planned
completion event is shown as an instant, not converted to a duration-bearing
execution.

The timing query compares recorded timestamps after normalizing their datatype
for comparison. Its predecessor check is intended for this single occurrence
per Step snapshot and skips conditional transitions; repeated executions need
explicit occurrence matching and branch evidence.

The Allen query needs inferred triples visible to the query engine, for example
after Pellet reasoning and loading an inference export into AllegroGraph.
Loading rule definitions alone does not run them. It uses only actual intervals
with both endpoints, excluding planned schedules and unfinished performances.
No rule or query invents completion, executes a workflow, or calls an LLM.

The Allen query was also checked with the 30 reasoner-inferred relations between the six completed actual intervals: it returns all 30 ordered, non-self pairs.
